사용자의 쿼리를 특징 벡터로 변환하고 모델에 입력해 채점 후 사용자에게 결과 반환

서버나 사용자 기기에 배포/ 한번에 모든 사용자에게 배포/ 일부 사용자에게 배포

**모델 배포 패턴**

1. 설치 가능한 소프트웨어 패키지의 일부로 정적 방식으로 배포
2. 동적 방식으로 사용자 기기에 배포
3. 동적 방식으로 서버에 배포
4. 모델 스트리밍을 통해 배포

### 1. 정적 배포

기존 sw 배포와 매우 유사. 설치 가능한 소프트웨어 바이너리를 준비하고 런타임에 사용할 수 있는 리소스로 모델 패키징. (apk, exe 등에 모델을 포함해 배포)

정적: 앱과 모델이 한몸(설치할 때 모델도 함께)

장점

- 소프트웨어에서 모델을 직접 호출해서 실행시간이 빠름
- 서버에 사용자의 데이터를 업로드 할 필요가 없어 시간 절약, 개인정보 보호
- 오프라인 상태에서도 가능
- 모델 운영 유지에 신경을 쓸 필요 없음. 사용자가 책임

단점

- 머신러닝 코드와 앱 코드의 구분이 명확하지 않음
- 전체 앱을 업그레이드 하지 않고는 모델을 업데이트 할 수 없음
- 디바이스 성능에 제약을 받음

### 2. 사용자 기기에 동적 배포

앱에서는 ‘모델 로더’만 내장하고, 모델 파일은 서버에서 다운로드해 디바이스에 캐시하는 방식

동적: 앱과 모델이 분리(앱 실행 중에 모델 다운OR실행)

1. 모델 매개변수 배포
    
    모델 구조(코드)는 이미 앱 안에 있고 서버에서 매개변수 파일만 내려보내는 방식
    
2. 직렬화된 객체 배포
    
    모델 전체(구조 + 매개변수 + 부가 정보)를 한개의 객체로 직렬화 해서 내려보내는 방식
    
    모델을 직렬화 해서 서버같은데 올리고 나중에 기기에서 로드해서 사용
    
3. 브라우저에 배포
    
    웹 사이트에 들어가거나 특정 버튼을 눌러 필요할 때 모델 다운로드 되어서 추론
    
4. 장점과 단점
    
    장점: 
    
    사용자가 모델을 빠르게 호출, 연산은 사용자의 기기에서 수행 → 서버 부하 감소
    
    단점:
    
    모델을 브라우저에 배포하는 경우 대역폭 비용 증가, 앱 시작 시간이 늘어남(웹 응용 프로그램을 시작할 때마다 모델의 매개변수를 다운해야 하기 때문)
    
    모델이 크면 업데이트가 오래 걸리는데 일부 사용자는 업데이트 중에 오프라인 상태가 되고 불편한 사용자는 이후 업데이트를 해제할 수 있다 → 사용자마다 모델 버전이 달라짐
    
    그리고 다른 사람이 모델 분석해 약점을 찾아내거나 데이터를 조정해 악용할 가능성
    
    모델 성능을 모니터링하기 어려움
    

### 3. 서버에 동적 배포

가장 인기있는 방식: 모델을 하나(또는 다수)의 서버에 배포하고 웹 서버나 **구글 원격 프로시저** 호출 서비스 형태의 **REST API**로 제공

REST API? → HTTP를 이용해 자원(리소스)를 주고받는 약속/스타일

1. 가상 머신에 배포
    
    물리 서버 위에 OS까지 포함된 가상 서버를 여러개 만들고 그 안에 앱/모델을 설치해서 돌리는 방식
    
    가상머신 하나마다 os 그 위에 런타임(파이썬 자바 등) + 앱/모델을 설치해 서비스
    
    일반적인 웹 서비스 아키텍처에서 클라우드 환경에 배포된 모델의 **예측**은 **정형화된 형식의 HTTP 요청에 대한 응답**으로 서빙.
    
    높은 부하에 대비해 여러개의 동일한 가상 머신이 병렬로 실행됨
    
    **로드 밸런서**: 한 곳으로 사용자가 몰리는것을 막아주는 장치
    
    **오토 스케일링 그룹**: 서버 여러대를 하나의 묶음으로 관리하면서 필요할 때 자동으로 늘리고 줄이는 기능 (사림이 몰릴때 안그럴때/ 서버 한대가 고장났을 때 등에 대비)
    
    파이썬은 Flask, FastAPI등으로 REST API 웹 서비스 구현
    
    서브(물리/가상)을 유지보수 해야하는 단점.
    
    가상화를 사용하는 경우, 가상화와 여러 운영체제 실행으로 인해 추가적인 컴퓨팅 비용이 발생한다. 
    
    **네트워크 지연 시간** - 클라이언트에서 서버로 요청을 보내고 서버가 응답을 보내기 시작하기 까지 걸리는 시간
    
    컨테이너 배포, 서버리스 보다 **비쌈**
    
2. **컨테이너에 배포**
    
    하나의 os위에서 애플리케이션만 여러개 분리해서 패키징하고 실행하는 방식
    
    물리 서버 1대 위에 호스트 os와 컨테이너 런타임을 두고 그 위에 컨테이너 여러개
    
    가상 머신보다 자원 효율적이고 유연.
    
    가상 머신과 유사 - 자체 파일 시스템, CPU, 메모리, 프로세스 공간이 있는 격리된 런타임 환경
    
    **컨테이너** - 모든 컨테이너가 동일한 가상/물리 시스템 에서 실행되고 운영체제를 공유. os에서 더 많은 인스턴스(os가 같아서)
    
    **가상 시스템** - 별도의 운영체제 인스턴스
    
    **배포 프로세스**
    
    - 머신러닝 시스템과 웹 서비스를 컨테이너 내부에 설치
    - **컨테이너 오케스트레이션 시스템**을 통해 물리/가상 서버 클러스터에서 컨테이너를 실행
        
        컨테이너 오케스트레이션 시스템이 뭔가? - 수십~수백 개의 컨테이너를 대신 관리/배치/확장/복구해주는 “컨테이너 운영 매니저” (Kubernetes)
        
        왜 필요할까? 서버 1개면 사람 손으로 관리 할 수 있음
        
        그러나 서버가 여러개/컨테이너가 수십~수백개일때 사람이 직접 어떤 
        
        서버에 어떤 컨테이너 띄울지 고민, 
        
        죽은 컨테이너 감지해서 다시 띄우기, 
        
        트래픽에 따라 컨테이너 늘리거나 줄이기, 
        
        업데이트를 매번 수동으로 하기 힘듦
        
    
    **자원 효율성**
    
     요청에 따라 확장/축소.
    
    **scale-to-zero** - 사용자가 없으면 서버(컨테이너/인스턴스) 개수를 0개까지 줄여버리는 스케일링 방식
    
    **cold start** - 0에서 1로 올릴때 (새 컨테이너/인스턴스 생성, 이미지 pull, 앱 로딩) 등 이 시간이 딜레이로 나타남
    
3. **서버리스 배포**
    
    서버를 직접 관리하지 않고 클라우드가 알아서 필요할 때만 실행해 주는 형태의 배포 방식
    
    서버가 없다x → 서버 관리를 신경 안써도 된다
    
    - FaaS (Function as a Service) - 함수형 서버리스
        - 함수 하나 단위로 코드 올림
        - 이벤트가 올 때만 실행:
            - HTTP 요청
            - 메시지 큐 이벤트
            - 파일 업로드 등
        - 요청없으면 scale-to-zero, 요청 들어오면 그때 컨테이너/런타임을 띄워서 함수 실행 후 종료
    - 서버리스 컨테이너/ 서버리스 플랫폼
        - 컨테이너 단위로 올리지만 운영은 서버리스처럼 해줌
            - Docker 이미지만 주면 나머지(스케일링, 인프라)는 플랫폼이 관리
        - HTTP 요청수에 따라 컨테이너 수를 자동으로 늘리고 없으면 0까지 줄이기도 함
    
    **장점**
    
    - 서버 관리 X
        - 어떤 인스턴스 타입을 쓸까
        - CPU 70% 넘으면 몇 대 더 늘릴까?
        - 오토스케일링 그룹 어디까지 늘릴까 등 클라우드가 알아서 처리
    - 비용 효율
    - 빠른 개발/배포 - 그냥 함수/컨테이너만 올리면 끝
    - 카나리 배포/ 카나리 작업을 간단하게 할 수 있음
        - 카나리배포 : 새 버전 서비스를 트래픽의 일부에게만 먼저 적용해서 이상 없으면 점점 늘리는 방식
    
    **단점**
    
    - 콜드 스타트
    - 장기 실행에 불리 (FaaS에서 실행 시간 제한)
        - 긴 배치 작업, 스트리밍, 긴 학습 작업에는 적합하지 않음
    
    **언제 쓰면 좋을까?**
    
    - 트래픽이 들쭉날쭉하거나 적을 떄
    - 사내/관리용 API, 툴, 크론 작업
    - 이벤트 기반
        - 파일 업로드
        - 메시지 큐/이벤트
    1. 모델 스트리밍 (이부분은 잘 모르겠네요. 책의 내용이)
        
        rest api의 역과정?
        
        내가 이해한 것. (음악 스트리밍과 유사하게 모델을 조금씩 다운받는 즉시 사용자의 요청 수행, 생성형인 경우 답변을 내보내면서 다음 입력으로 쓰는 등)
        
        모델을 하나의 큰 파일로 배포하지 않고, 여러 조각으로 나눠서 네트워크로 조금씩 전달/로딩
        
        모델 파일을 한 번에 받지 않고 필요한 부분을 네트워크로 조금씩 가져오면서 쓰는 방식
        
        모델이 크면 첫 실행이 느림 → 필요한 만큼만 쓰자
        

### 4. 배포 전략

1. 단일 배포
    
    새 모델이 있으면 직렬화 해서 교체
    
    물리적 서버 - 서버에 새 파일, 모델을 업로드하고 이전 파일과 코드를 새 버전으로 교체
    
    단순하지만 버그가 있으면 치명적
    
2. 자동 배포
    
    모델이나 코드가 변경되면 사람이 수동으로 배포하지 않고 미리 정해둔 절채대로 시스템이 알아서 빌드, 테스트, 배포까지 진행하는 방법
    
    CI - 단위 테스트, 통합 테스트 정정 분석 등 자동으로 테스트
    
    CD - 검증용 환경으로 자동 배포
    
    새 모델과 특징 추출기를 배포하면서 이전 버전도 유지.
    
    사용자는 전환이 완료될 때까지 새 버전에 노출x
    
    새 버전의 예측을 기록하고 버그가 있는지 검사(충분히 테스트 할 수 있음)
    
    버전 2개를 유지하는데 비용이 많이드는 경우, 새 모델의 예측값을 사용자에게 노출하지 않고는 새 모델을 평가하기 어렵다
    
3. 카나리 배포
    
    새 버전 모델과 코드는 소수의 사용자에게만 푸시, 나머지 대부분은 이전 버전
    
    새 모델의 예측과 성능을 검증할 수 있고, 버그가 있을때 큰 영향이 없음
    
    여러 버전의 모델을 배포하고 유지 관라하는데 따르는 추가적인 복잡도는 수용할 만함
    
    눈에 잘 띄지 않는 오류를 발견하기 어려운 단점 (소수의 사용자에다가 버그 영향을 미치는게 낮으면 전체적으로 발견하기 매우 어려움)
    
4. 멀티 암드 밴딧
    
    여러가지 팔(모델 버전)의 성능을 비교해 더 좋은 쪽으로 비율을 높이는 방식
    
    온라인 모델 평가와 모델 배포라는 두가지 문제를 동시에 해결할 수 있음
    

### 5. 자동화된 배포, 버전 관리, 메타데이터

1. **모델에 수반하는 항목**
    - 항상 작동 해야하는 모델 입력과 출력을 정의하는 **end-to-end set**
        
        입력/출력 스펙 + 항상 통과해야 하는 대표 케이스들
        
    - 모델 입력과 출력을 정의하고 지푯값을 계산하는 데 사용하는 **신뢰도 테스트 세트**
    - 신뢰도 테스트 세트에 적용한 모델을 통해 계산된 값을 찾는 **성능 지표**
    - 성능 지표의 혀용 가능한 **값의 범위**
    
    → 모델을 저굥ㅇ한 시스템이 서버나 사용자의 기기의 인스턴스에서 처음 호출되면, 외부 프로세스에서 종단 간 테스트로 모델을 테스트하고 모든 예측이 올바른지 확인. 또한 성능 지표가 허용 가능한 범위 내에 있는지 확인
    
2. 버전 동기화
    - 훈련 데이터
    - 특징 추출기
    - 모델
    
    위 3가지 요소는 항상 동기화 되어 있어야 함
    
    데이터를 업로드 할 때마다 데이터 저장소에 새 버전을 만들어야 함
    
    특정 버전의 데이터로 훈련한 모델은 해당 버전과 동일한 버전으로 저장
    
    특징 추출기가 변경되지 않았더라도 동기화 시켜 버전 업데이트
    
3. 모델 버전 관리를 위한 메타데이터
    
    모델 버전 관리를 위해 아래 코드, 메타 데이터를 함께 제공
    
    - 모델 훈련에 사용한 라이브러리, 패키지 이름 버전
    - 파이썬으로 모델 구축할때 가상 환경의 패키지 설치 목록을 기록한 requirements.txt파일
    - 학습 알고리즘의 이름, 초매개변수의 이름과 값
    - 모델에 필요한 특징 목록
    - 출력물 목록, 유형, 사용 방법
    - 모델 훈련에 사용한 데이터의 버전과 위치
    - 모델의 초매개변수를 조정하는 데 사용한 검증 데이터의 버전과 위치
    - 새 데이터로 모델을 실행하고 예측을 출력하는 모델 채점 코드
    
    품질 검사 정보
    
    - 누가 언제 모델 구축했는지
    - 누가 언제 어떤 근거로 해당 모델을 배포하기로 결정했는지
    - 모델에 대한 개인정보 보호와 보안 준수사항을 누가 검토했는지
