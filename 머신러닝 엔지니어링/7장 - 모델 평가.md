운영환경에서 모델 평가는 신중해야함 (법적 책임 위험이 있을 수 있음)

목표 정의 → 데이터 수집/준비 → 특징공학 → 모델 훈련 → **모델 평가** → 모델 배포 → 서빙 → 모니터링 → 유지보수

**평가할 것들**

- 모델을 운영 환경에 투입할 때 법적 위험 추정
    - ex) 기밀 정보를 간접적으로 내포할 수 있음
    - 연령/ 성별/ 인종과 같은 특징을 잘못 사용하면 조직이 편향되거나 차별적이라고 비춰질 수 있음
- 훈련에 사용하는 데이터와 운영 환경에서 처리하는 데이터 분포의 주요 특성을 비교 연구
- 모델의 성능 평가
    - 훈련에 사용하지 않은 데이터로 예측 성능 평가.
    - 운영환경의 과거 샘플과 온랑니 샘플을 모두 포함하고 있어야 한다
- 배포한 모델 성능 모니터링
    - 시간이 지날수록 성능이 저하될 수 있음
    
1. 오프라인 평가/ 온라인 평가
    - **오프라인**
        - 분석가가 모델을 훈련할 때 수행 - 다양한 특징, 모델, 알고리즘, 하이퍼파라미터를 테스트
        - confusion matrix, 정밀도, 재현율, AUC 같은 지표
    - **온라인 평가**
        - 고객 만족도, 온라인에 머무르는 시간, 공개 비율, 클릭률 같은 비즈니스 결과를 측정.
        - 오프라인 평가에서는 온라인에서 관찰할 수 있는 세션 연결, 데이터 손실, 통화 지연과 같은 조건에 대해서 모델을 테스트할 수 없다
    
    배포한 후 에 지속적으로 모니터링. 온라인 데이터의 성능이 저하되면 모델을 다시 훈련해야함
    

### 2. **A/B 테스트**

새 모델과 기존 모델 중 뭐가 운영환경에서 더 잘 작동할까?

→ 새 모델이 이 특정 비즈니스 지표에서 통계적으로 유의미한 변화를 가져오는지?

트래픽을 두 그룹으로 나눠 일부는 이전 모델(A)로 라우팅, 나머지 일부는 새 모델(B)로 라우팅

**귀무 가설/ 대립 가설**과 같은 통계 가설 검정으로 성능 비교

**귀무가설** - 새 모델이 비즈니스 측정 항목의 평균값을 변경하지 않음 (A나 B나 차이없다로 가정)

**대립 가설** - 새 모델이 지표의 평균값을 변경한다 (B가 A와 다르다[보통 더 좋다]로 가정)

→ 관찰된 차이가 우연으로 나올 확률을 계산. 노이즈에 속지않고 오판 확률을 관리해 배포 결정을 하기 위해 가설 세움

**새 버전이 진짜로 좋아진 건지, 아니면 그냥 샘플이 그렇게 나온 건지를 통계적으로 판별하는 절차**

1. **G-테스트**
    
    yes or no로 답할 수 있는 질문에 다한 답을 계산하는 지표에 적합
    
    ex) 사용자가 추천 기사를 구입했는지, 구독을 갱신 했는지 등등
    
    적용
    
    - 새 모델이 이전 모델보다 좀 더 잘 작동하는지 여부를 결정하기 위한 지표 정의하는 질문 만듦
    - 사용자를 그룹 A와 B로 나눠 각각 이전모델과 새 모델에 할당
    - 사용자의 행동을 관찰해 예/ 아니오 대답을 작성
    - A와 B에 대한 예/아니오 예상 응답수로 G-테스트의 값을 찾음
    - G: A와 B의 샘플이 얼마나 다른지. (A 와 B가 같으면 G가 작을것으로 예상)
    - ex) G = 3.84이고 A와 B가 같으면 G ≥ 3.84일 확률을 5%. 이 확률을 p라고 함
    - p값이 충분히 작으면 새 모델과 이전 모델의 성능이 매우 다를 가능성이 높다(귀무 가설 기각). B_yes 값이 높으면 새 모델이 더 좋다
    - 작지 않으면 성능차이가 통계적으로 유의하지 않음
        
        → 관찰값과 기대값이 얼마나 다른지 보는 검정
        
        최소 10개의 yes/no면 유효하지만 그대로 받아들이지 말것.
        
    
    유형별로 100개 이상 → 몬테카를로 시뮬레이션
    
    2개 이상의 모델과 2개이상의 가능한 답을 테스트 할 수 있음.
    
    좀 복잡한 편
    
    2개 이상이 모델이 있을 때 완전탐색 느낌으로 테스트를 해보고 싶을텐데 안좋다고 함.
    
    → 왜? 
    
    1. 다중 비교(multiple comparisons) / 1종 오류 폭발
        - 쌍의 개수 = n(n−1)/2 → 검정 횟수가 **폭발적으로 증가**
        - 결국 “우연으로 좋아 보이는 모델”을 진짜 우승자로 뽑게 될 가능성이 확 올라감
    2. 동일한 샘플을 여러번 재활용하는 꼴.
        
        A < B 이고 B < C 이지만 A와 C는 유의미하지 않다 같은 결과가 나올수도 있음
        
2. **Z-테스트**
    
    질문이 얼마나? (how many/ how much)일때 적용
    
    ex) 사용자가 세션 동안 웹 사이트에서 보낸 시간은 얼마인가?, 한달동안 지출한 비용은 얼마인가?
    
    전체적인 틀은 비슷
    
    웹 사이트에서 보낸 시간을 표본분산을 구해 Z값을 구함.
    
    Z값이 클수록 통계적으로 유의
    
    유의 수준이 5%인 경우 p값이 0.05보다 작으면 귀모가설 기각
    
3. **결론 및 주의사항**
    
    예시일 뿐 특정 비즈니스 문제엔 적합하지 않을 수 있음. A/B 테스트 코드를 주의깊게 테스트해야 함. 그리고 그룹A/B를 동시에 측정해야 함.
    
    그리고 교체 비용도 고려해야 함
    

### 3. 멀티 암드 밴딧

A/B테스트: 통계적으로 의미 있는 차이를 보려면 표본 수가 많아야 함,

**탐색-활용 딜레마:**  차선의 모델버전을 실제 유저에게 최대한 적게 노출시키면서도 표본 수를 얻기 위해 어느정도 보여줘야 함.

**멀티 암드 밴딧 문제**

모델이 여러개가 있지만 각 모델이 얼마나 좋은지 모름.

하나를 골라 그 선택으로 부터 보상(클릭, 전환 등) 을 관찰할 수 있다

→ 계속 선택하면서 어떤게 좋은지 학습. 전체 기간 동안 얻는 보상도 초기화

정리: 모델 3개 (A,[기존], B[새거], C[새거]): 각 요청마다 A,B,C를 사용할지 선택

결과를 보고 어떤게 더 잘 먹히는지 업데이트 → 시간이 지날수록 더 좋은 모델에 트래픽을 많이

A/B는 트래픽을 정해놓고 분배 → 실험이 끝나고 결정

**UCB1** 알고리즘- 멀티 암드 밴딧 문제를 해결하는데 많이 사용

### 4. 모델 성능에 대한 통계적 한계

때로 모델 성능을 보고할 때 지푯값 외에 **통계구간(statisstical interval)**이라 하는 통계 한계도 제공해야 함

95% 통계 구간 - 추정하는 매개변수가 구간의 양 경계 사이에 있을 가능성이 95%

1. **분류 오류에 대한 통계 구간**
    
    err = 1-정확도 여기선 p로 둠
    
    95% 신뢰구간
    
    ![image.png](attachment:ceb020cf-aafd-4ca9-aaff-827cf46bdefe:image.png)
    
2. **부트스트래핑 통계 구간**
    
    왜 부트스트랩을 쓰나? - 신뢰구간을 만들려면 통계량의 분포 형태를 알고있어야 함(평균, 비율)
    
    실전에서는 f1-score, AUC등 통계량이 복잡 → 데이터 재 샘플링해서 통계량을 직접 추정
    
    1. 부트스트랩: 원본 데이터에서 복원추출로 표본 n개 추출
    2. 각 부트스트랩 샘플에서 통계량 계산
    3. 이 분포에서 구간 뽑기 - 95% 부트스트랩 신뢰구간 → 하위 2.5퍼센타일 값 ~ 상위 97.5퍼센타일 값
3. **회귀를 위한 부트스트래핑 예측 구간**
    
    비슷하지만 여기에선 훈련 샘플에서 부트스트랩 샘플을 만들어 각 샘플에 대한 모델을 만든다.
    
    최댓값 최솟값 사이 가장 좁은 간격을 찾아 그 구간에 있는 예측값의 합이 최소 c%가 되게 함
    
    그런 다음 예측 반환하고 신뢰도 c퍼센트로 구간 [a,b]에 있다고 할 수 있다
    

### 5. 테스트 세트 적합성 평가

머신러닝 코드(사용자의 입력을 받아 특징변환, 출력 해석하고 결과를 사용자에게 서빙하는 코드)를 테스트에 적용. 모델 자체에 대해서는 별도의 평가

1. **뉴런 커버리지** - 치명적인 영향을 미칠 수 있는 시나리오(자율 주행, 우주 로켓 등)
    
    테스트 데이터들이 신경망 안의 뉴런을 얼마나 골고루 깨워봤는지를 수치화(활성화 한 뉴런 비율)
    
2. **돌연변이 테스트**
    
    일부러 살짝 버그같은 걸 심어놓고 우리의 테스트가 그것을 잡아내는지 보는 기법
    
    돌연변이 프로그램에서 기존 테스트 중 하나라도 실패하면 ‘**돌연변이를 죽였다’**라고 함
    
    머신러닝에서는 **훈련 데이터를 수정**하거나 모델이 깊으면 **랜덤하게 층을 추가하거나 제거, 활성화 함수를 바꾸거나 제거** 등을 할 수 있음
    
    훈련 데이터에선 - 중복 샘플 추가, 일부 샘플 레이블 위조, 일부 샘플 제거, 일부 특징에 잡음 추가
    

### 6. 모델 특성 평가

정확도나 ROC 곡선 아래 영역 같은 지표로 평가할 수 있지만. 강건성 공정성과 같은 다른 특성을 평가하는 것이 적절할 수 있다.

1. **강건성** - 입력 데이터에 약간의 잡음을 추가 했을 때 모델 성능의 안정성
    
    강건한 모델은 잡음 크기에 비례해 모델의 성능이 저하됨 → 노이즈가 조금이면 성능도 조금만 떨어지고, 노이즈가 많이 커지면 그에 맞춰 점진적으로 떨어지는, 과하게 민감하지 않은 모델
    
    **강건하다** → 입력을 조금(ε만큼 까지는) 흔들어도 모델이 크게 바뀌지 않는다
    
    성능 지표에 따라 유사한 성능을 보이는 모델이 여러 개 있는 경우 테스트에 적용할 때 견고한 모델을 배포하는 것이 좋다. 
    
2. **공정성** - 누구에게 얼마나 ‘공평하게’ 잘 동작하는지
    
    머신러닝 알고리즘은 인간이 교육하는 것을 학습하는 경향이 있음.
    
    인간은 데이터 수집과 레이블링 방법에 영향을 미칠 수 있는 편견을 가지고 있고, 역사적, 문화적, 지리적 데이터에도 편견이 존재함.
    
    **보호된 속성/민감한 속성** - 민감하고 불공정성으로 보호가 필요한 속성(인종, 성별, 국적, 종교, 등등)
    
    공정성은 도메인 별로 다르며 각 도메인에는 고유한 규정이 있을 수 있다(신용, 교육, 고용, 주택 등등)
