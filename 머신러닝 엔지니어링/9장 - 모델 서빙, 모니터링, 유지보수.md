### 1. 모델 서빙 런타임의 특성

모델 서빙 런타임 - 모델을 입력 데이터의 적용하는 환경. 배포 패턴에 따라 결정

효과적인 런타임 특성

1. 보안 및 정확성
    
    런타임은 사용자 인증과 사용자 요청 승인을 담당
    
    확인해야 할 사항
    
    - 특정 사용자가 실행하려는 모델에 대한 접근 권한이 있는지
    - 전달된 매개변수의 이름과 값이 모델 규격과 일치하는지 여부
    - 이러한 매개변수와 매개변숫값이 현재 사용자에게 제공되는지 여부
2. 배포 용이성
    
    런타임은 최소한의 노력으로 전체 앱에 영향을 주지 않고 모델을 업데이트 할 수 있어야 함
    
    가상 머신 인스턴스나 컨테이너로 배포한 경우, 이전 버전 실행 중인 인스턴스를 점점 중지해 가면서 새 인스턴스를 실행하는 방식
    
3. 모델 유효성 보장
    
    효과적인 런타임은 실행중인 모델이 유효한지 자동으로 확인한다. 모델, 특징 추출기, 기타 구성요소가 동기화 되어있는지 확인.
    
    서비스를 실항할 때마다 그리고 실행시간동안 주기적으로 검증
    
    종단 간 세트, 신뢰도 테스트 세트, 성능 지표, 허용 가능한 값의 범위등 4가지 항목과 함께 배포해아 함
    
    - 적어도 하나 이상의 종단 간 테스트 샘플이 올바르게 채점되지 않았다
    - 신뢰도 테스트 세트 견본에서 계산한 지푯값이 허용 범위를 벗어났다
    
    위 2가지 중 하나라도 해당되면 서빙하면 안됨
    
4. 복구 용이성
    
    효과적인 런타임을 사용하면 이전 버전으로 롤백하여 오류를 쉽게 복구할 수 있다
    
5. 훈련/서빙 왜곡 방지
    
    모델 훈령용과 운영환경의 채점용 이렇게 다른 코드 베이스를 사용하지 않아야 함(특징 추출시 2개의 추출기에 조금의 차이도 있으면 성능이 부정확해짐)
    
    런타임을 통해 모델 재훈련, 임시 모델 호출, 운영 환경에서의 다양한 요구가 있을 때 특징 추출 코드에 쉽게 접근할 수 있어야 함.
    
6. 숨겨진 피드백 루프 방지
    
    피드백루프: 시스템의 결과가 다시 그 시스템의 입력에 영향을 주는 시스템
    
    훈련 데이터가 자연스럽게 생긴 것이 아니라 모델이 개입한 새계에서 수집된 변형된 데이터 → 편향
    
    사용자에게 인기있는(?) + 인기없는(?) 신규 를 같이 보여주는 방식으로 해결
    

### 2. 모델 서빙 모드

1. 배치 모드 서빙
    
    대량의 입력 데이터에 모델을 적용할 때
    
    ex) 제품이나 서비스의 모든 사용자의 데이터를 모델로 처리하는 경우, 트윗이나 온라인 게시물에 대한 댓글과 같은 모든 수신 이벤트의 종류에 따라 모델을 체계적으로 적용하는 경우.
    
    자원 효율성 높음, 약간의 시간 지연
    
    → 미리 모델을 돌려 예측을 데이터베이스에 저장하고 필요할때 db에서 읽기만 함
    
2. 인간에 대한 주문형 서빙
    
    요청이 들어올 때마다 그때그때 모델을 돌려서 결과를 만드는 방식
    
    사용자가 뭔가를 할때마다 그 시점의 실시간 컨텍스트(유저 상태, 최신 로그, 현재시간, 위치 등)을 입력으로 넣고 모델의 결과를 응답으로 보내줌
    
    채점 결과를 그대로 내보내지 않고 쉽게 해석할 수 있게 변환 후 전달
    
    인간에게 모델을 서빙하기 전에 예측 신뢰도 점수를 측정. 낮으면 아무것도 제공하지 않을 수 있다.
    
    모델 서빙할 때 컨텍스트와 사용자의 반응을 기록하면 편리
    
3. 머신에 대한 주문형 서빙
    
    REST API도 하지만 종종 스트리밍을 통해 머신에게 서빙한다
    
    주문량이 일정하지 않아 낮에는 높고 밤에는 낮을 수 있음 → 클라우드에서 가상 자원을 사용하는 경우 오토 스케일링을 통해 자원 관리 → 갑작스러운 수요 급증에 민첩하게 대응하지 못할 수 있음 → RabbitMQ나 아파치 카프카와 같은 메시지 브로커가 있음
    

### 3. 현실에서의 모델 서빙

일반적으로는 모든 사용자의 행동과 반응을 예측하는 것은 불가능. 현실적인 소프트웨어 시스템의 아키텍처는 오류, 변화, 인간 본성이라는 3가지 상황에 대비

1. 오류에 대한 대비
    
    오류는 불가피한 부분. 모든 오류를 해결할 수 없기 때문에 오류가 발생해도 시스템이 계속 정상적으로 동작할 수 있도록 소프트웨어 설계
    
    인정하고 수용해야만 하는 “할 수 없는 것”
    
    - 오류가 발생한 이유를 모두 설명할 수 없다
    - 오류가 언제 발생할지 확실하게 예측할 수 없으며, 높은 신뢰도의 예측조차도 틀릴 수 있다
    - 모든 특정한 오류를 수정하는 방법을 알 수는 없다. 수정할 수 있다고 해도 어떤 종류의 훈련데이터가 얼마나 필요할지 알 수 없다.
    
    또한 오류로 인해 잘못된 예측이 항상 올바른 예측에서 크게 벗어나지 않을 거라고 기대할 수 없음.
    
    맥락이 조금만 바뀌어도 예기치 않은 패턴의 오류가 발생할 수 있다. (ex. 위험 상황 인식에서 조명이 바뀔때)
    
    사용자 수가 많아지면 드물게 발생하는 오류라도 많은 사용자에게 영향을 미칠 수 있다
    
    오류를 하나 수정했는데 다른 오류가 생길 수도 있음
    
2. 오류 처리
    - 적어도 부분적으로라도 시스템이 어리석은 것처럼 보이거나 행동하는 상황을 완화하기 위한 전략을 세워야 함(ex) 챗봇에서 답변이 어려울 경우 아무거나 말하는 것보단 모르겠다고 말하는 것이 좋다.
        
        오류가 사용자에게 직접 노출되는 경우 예상 오류 비용을 계산하고 임계값 초과하면 사용자에게 예측결과를 알려주지 않는다
        
    - 모델 a가 오류를 범할 가능성을 예측하는 모델 b를 훈련.
        
        모델 a의 예측이 치명적인 영향을 미치는 시스템일때
        
    
    오류의 가시성 - 오류를 숨기는 여부와 숨기는 방법을 결정하는 요소(오류가 밸생했을 때 사용자가 인지하고 이해할 수 있도록 하는 원칙)
    
    가시성이 높은 오류
    
    - 비밀번호 오류 → 비밀번호가 틀렸다고 알림 뜸 → 눈에 띄게 드러남
    - 서버에서 db 연결 실패 → 에러 로그에 기록 → 개발자가 원인 추적 쉬움
    
    가시성이 낮은 오류
    
    - 추천 시스템이 다르게 추천 → 사용자는 조용히 나감 → 시스템 입장에서는 오류가 있었는지도 모름 → 에러가 있지만 표시, 피드백 없음
    - 머신러닝 모델이 소수 집단에서만 성능 낮음, 전체 지표는 준수 → 세부 그룹 단위로 안보면 문제인지 x → 오류는 있지만 지표상으론 잘 안보임
    
    높이는 법: 구체적인 에러 미시지, ui에서 눈에 띄는 피드백, 버튼/피드백 추가 등등
    
    아래 내용은 적긴하지만 감이 잘 안잡히는 것들
    
    가장 피하고 깊은 오류 유형 결정 후 예측 임계값을 포함하는 초매개변수 최적화
    
    최고의 예측 결과에 대한 신뢰도가 낮으면 몇가지 옵션 제시
    
    모델에 대한 사용자의 노출을 조절해 불만을 피하는 방법 (사용자가 감당할 수 있는 오류 수 추정해 모델 간 상호작용 제한)
    
    사용자가 오류를 감지하고 해당 오류를 보고하는 것에 대비
    
    사용자의 시스템 사용도를 측정하고 모든 상호작용을 기록한 다음 의심스러운 상호작용을 분석 
    
3. 변화에 대한 준비 및 대처
    
    일반적으로 머신러닝 기반 시스템의 성능은 시간이 지남에 따라 변함. 실시간으로 변할 수도.
    
    품질이 좋아지거나 나 빠질 수 있음
    
    일부 입력에 대한 예측이 달라질 수 있음
    
    일부 변화는 긍정적으로 인식할 수 잇지만 성능이 좋아지더라도 부정적으로 인식할 수 있다.
    
    사용자는 특정 행동에 익숙해지는데 변화로 결과가 달라진다면 불편함을 느낄 수 있음
    
    변화를 부정적으로 인식할 수 있다고 예상되는 경우, 적응할 시간을 주고 변경 사항과 새 모델에서 기대할 수 있는 사항을 교육. 또는 변화를 점진적으로 도입
    
4. 인간 본성에 대한 준비 및 대처
    
    인간은 예측할 수 없고 종종 비합리적이고 일관성이 없으며 기대치가 명확하지 않지만 견고한 소프트웨어 시스템은 이를 예측할 수 있어야 함
    
    - 혼란 방지
        
        사용자가 시스템과 상호 작용하는 데 혼란을 느끼지 않도록 설계해야 함
        
    - 기대치 관리
        
        일부 광고를 접한 사용자는 기대치가 높음. 이런 사용자는 시스템에서 동일한 수준의 ‘지능’을 기대
        
    - 신뢰 확보
        
        경험 많은 사용자는 시스템에 ‘지능’이 포함되어 있다는 것을 알면 시스템을 불신하는 경향. → 각 사용자의 신뢰를 얻어야 하며 이를 조기에 완수해야 함.
        
        ‘지능형’시스템 경험해 본사람은 간단한 테스트를 수행할 가능성이 높다. 이때 오류가 발생하면 시스템을 신뢰하지 않음 → 서비스에 따라 간단한 테스트를 예상하고 시스템이 테스트를 통과하는지 확인해야 함
        
    - 사용자 피로 관리
        
        시스템이 권장 사항이나 승인 요청으로 사용자 경험을 과도하게 방해하지 않는지 확인. 사용자에게 필요한 모든것을 한 번에 보여주는 것을 피하고 가능하면 사옹자가 관심을 명시적으로 표현하도록 함
        
    - 크리프 팩터 주의
        
        사용자가 학습 시스템과 상호작용 할때 시스템이 사용자 데이터를 많이 모으고 그걸로 개인화된 행동 추천 피드백을 해주는데 그 방식이 감시하거나 캐묻는다에 가깝게 느껴지는 상황.
        
        너무 세부적인 예측에 불편함을 느낌(정확해서 좋은 게 아니라, “어떻게 이걸 알지?” 싶어서 무서운 상태)
        

### 4. 모델 모니터링

모델이 올바르게 서빙되고 있는지, 성능이 허용 가능한 범위 내에서 유지되고 있는지

1. 무엇이 잘못될 수 있는가?
    
    운영환경에 배포한 모델이 문제 발생 시 이를 조기에 경고하도록 설계해야 함
    
    - 모델 업데이트에 사용한 새로운 훈련 데이터로 인해 성능이 저하되었다
    - 운영 환경에서의 실시간 데이터는 변경되었지만 모델은 변경되지 않았다
    - 특징 추출 코드가 많이 업데이트 되었지만 모델을 조정하지 못했다
    - 특징을 생성하는 데 필요한 자원이 변경되었거나 사용할 수 없게 되었다
    - 모델이 남용되거나 적대적 공격을 받고 있다
    
    추가 데이터가 항상 좋은건 아님 (레이블러가 레이블링 지침을 잘못 해성했을 수 있고, 한 레이블러의 결정이 다른 레이블러와 반대될 수 있고, 자동으로 수집된 데이터는 편행될 수 있다)
    
    때로는 운영환경에서의 데이터 속성이 점진적으로 변하지만 모델이 적응하지 못하는 경우도 있음(개념 이동 - 모델에 사용한 훈련데이터가 너무 오래되어 현실을 대표하지 못함)
    
    특징 추출 코드 변경했으면 모델도 업데이트
    
    특징 추출과 모델이 동기화되어 있더라도 일부 자원(db, api)이 사라지거나 변경되면 추출된 특징이 영향을 미칠 수 있음
    
    특히 전자 상거래와 미디어 플랫폼에 배포된 모델은 적대적 공격의 대상이 된다. 사용자의 행동을 통해 학습하는 경우 모델 동작을 그들에게 유리하게 변경하기 위한 시도를 할 수 있다.
    
    공격자는 학습 데이터에 대한 정보를 얻기 위해 훈련된 모델을 살펴보려고 할텐데, 기밀이 담겨 있을 수 있으니 주의
    
    이중 사용 - 선하게 사용되는 경우와 이를 악용해 사용할 수 있음(예방이 어려움)
    
2. 모니터링 대상 및 방법
    
    **신뢰도 테스트 세트**를 적용히 합리적인 성능 지표를 생성하는지 확인
    
    신뢰도 테스트 세트는 분포 이동을 방지하기 위해 정기적으로 업데이트, **종단 간 세트**의 샘플로 모델을 테스트
    
    시간 경과에 따른 변화를 측정하는데 유용한 지표 - **예측 편향** → 훈련 데이터 레이블의 분포와 운영 환경의 현재 클래스 분포가 다르다는 것
    
    **모델의 수치적 안정성** 모니터링 **-** NaN또는 무한대가 관찰되면 경고
    
    **머신러닝 시스템의 계산 성능** 모니터링 - 극적으로 떨어지는 것과 천천히 나빠지는 것 모두 감지하고 경고해야 함
    
    **사용량 변동**이 의심스러운 경우
    
    - 한 시간 동안 서빙 수 모니터링 후 하루 전에 계산한 값과 비교. 30% 이상 변경된 경우 경고
    - 일일 모델 서빙 수 모니터링 후 일주일 전에 계산한 값과 비교. 15%이상 변경된 경우 경고
    
    모니터링을 통해 수치의 원하지 않는 변화들
    
    - 최소 예측값, 최대 예측값
    - 주어진 기간 동안의 중앙값, 평균, 표준 편차 예측값
    - 모델 api 호출 시 지연 시간
    - 예측 수행 시 메모리 소비량과 cpu사용량
    
    분포이동 방지를 위한 모니터링 자동화
    
    - 일정 기간동안 랜덤으로 입력을 모음
    - 이 입력을 레이블링
    - 모델 실행 후 성능 지푯값 계산
    - 중대한 성능 저하 시 알림
    
    추천시스템일 경우 추가적인 모니터링 - 클릭률, 추천을 받은 총 사용자 수의 비율
    
    작은 변화를 너무 보수적으로 알리거나 너무 자주 알리는 것 사이의 절충
    
    전체 프로세스를 추적할 수 있도록 모니터링 이벤트 기록. 성능의 변화를 시각화
    
    모니터링 도구 중 하나는 데이터 슬라이스에 대한 지표를 계산하고 시각화 할 수 있는 기능
    
    모니터링 이외에 기록해야 하는 데이터
    
    - 문제의 원인을 찾는 데 도움이 되는 데이터
    - 실시간 분석이 불가능한 데이터
    - 기존 모델을 개선하거나 새 모델을 훈련하는 데 유용한 데이터
3. 기록할 내용
    
    향후 분석에 필요한 비정상적인 시스템 종작을 재현할 수 있도록 충분한 정보를 기록하는 것이 중요
    
    프론트엔드 사용자에게 서빙하는 경우 서빙 시점에서의 사용자 컨텍스트 등
    
    컨텍스트 - 웹 페이지의 컨텐츠(앱의 상태), 웹 페이지에서의 위치, 시간, 사용자가 에디에서 왔는지, 모델 예측 전 클릭한 내용
    
    컨텍스트로 부터 추출한 특징인 모델 입력과 특징을 생성하는 데 걸린 시간
    
    모델 출력과 출력을 생성하는 데 걸린 시간
    
    모델의 출력을 관찰한 후 사용자의 새 컨텍스트
    
    출력에 대한 사용자의 반응 (출력을 보고 난 후 취하는 즉각적인 행동. 무엇을 클릭, 출력을 서빙한 후 클릭까지 걸린 시간)
    
    규모가 큰 시스템은 모든 이벤트를 기록하기 어려움. → 계층화된 샘플링
    
    사용자 - (연령, 성별, 서비스 이용 기간), 컨텍스트 - (시간대별, 업무 등)
    
    사용자의 활동 데이터를 로그에 저장할 때 사용자는 데이터 수집 내용, 시기, 방법, 기간을 알아야 함. 데이터를 손실 없이 최대한 익명화, 통합. 민감한 데이터 관리 주의
    

4. 남용 감시

매일 수백만 건의 요청을 보내거나 훈련 데이터 역설계, 모델을 자신이 원하는 방향으로 출력을 생성하도록 할 수 있음

남용 방지 방법

- 요청당 비용 지불
- 여러 요청이 있을 때 점진적으로 응답 지연
- 일부 사용자 차단

일부는 자신의 비즈니스 목표를 위해 모델을 조작하려고 할 수 있다. 결과적으론 모델의 전반적인 품질 하락

방지 법

- 여러 사용자로부터 유사한 데이터가 제공되지 않는 한 사용자의 데이터를 신뢰하지 않음
- 각 사용자에게 평판 점수 할당. 낮은 사용자의 데이터는 신뢰하지 않음
- 사용자의 행동을 정상/비정상으로 분류. 비정상 사용자의 데이터는 받아들이지 않음.

공격자는 행동을 바꿔서 방어를 우회하려고 할 것이므로 모델을 정기적으로 업데이트.

### 5. 모델 유지보수

모델은 정기적으로 업데이트 하지만 다음 같은 상황에서는 빈도가 달라짐

- 오류 발생 빈도와 중요도
- 얼마나 ‘최신’모델이어야 하는지
- 새로운 훈련데이터를 얼마나 빨리 사용할 수 있는지
- 모델을 재훈련하는데 걸리는 시간
- 모델 배포하는데 드는 비용
- 모델 업데이트가 제품과 사용자 목표 달성에 기여하는 정도
1. 업데이트 시기
    
    처음 모델을 배포하면 대부분 완벽하지 않음. 일부 오류는 유해할 수 있으므로 업데이트 해야 함
    
    모델 신선도는 비즈니스 요구와 사용자의 요구에 따라 달라짐
    
    새 훈련 데이터를 얼마나 빨리 얻을 수 있는지도 업데이트 빈도에 영향
    
2. 업데이트 방법
    
    이상적인 방법은 시스템을 중단하지 않고 새 모델을 배포하는 것
    
    새 모델이 저장소에 저장되면 운영환경 런타임이 새 모델, 테스트 데이터, 테스트 데이터에 모델을 적용하는 코드를 코드를 가져옴
    
    새 모델이 테스트롤 통과하면 새 모델로 교체
    
    구글이 추천하는 우수한 구성 시스템
    
    1. 이전 구성에 대한 변경사항으로 현재 구성을 쉽게 나타낼 수 있어야 함
    2. 수작업에 따른 오류 누락 간과가 발생하기 어려워야 함
    3. 두 모델 간의 구성 차이를 시각적으로 쉽게 확인할 수 있어야 함
    4. 사용된 특징 수, 데이터 종속성 등과 같이  구성에 대한 기본 사실을 자동으로 확인하고 검증하는 것이 쉬워야 함
    5. 사용하지 않거나 중복된 설정을 감지할 수 있어야 함
    6. 구성은 전체 코드 검토를 거쳐 저장소에 체크인 해야 함
    
    오류는 피할 수 없다. 사용자 범주 간 오류가 균일하게 분포되어 있는지 확인.
    
    연속된 모델 사용시 주의
