### 인덱스가 필요한 이유

- 데이터가 엄청 많아져서 테이블이 커진 경우 쿼리가 실행되는 시간이 점점 늘어난다
- **풀 테이블 스캔** : 인덱스가 없는 테이블에서 특정 데이터를 찾는 것은 100만페이지 짜리 큰 책에서 특정 단어를 찾기 위해 1페이지부터 끝까지 한장씩 찾아보는 것과 같다
    - 최선의 경우: 첫 행에 나타날 수 있음. → 1번 비교
    - 최악의 경우: 마지막 행에 있거나 없을 경우 → 100만번 비교

### 데이터 양에 따른 성능 저하

- 서버의 사양, 환경설정, 데이터 한 행당 크기, 시스템의 현재 부하 등 변수에 따라 달라지겠지만 데이터가 많아지면 느려지는건 같다.

### 페이지 로딩 속도에 대한 연구

- 1초 → 3초로 늘어나면 이탈률 32%증가
- 1초 → 5초로 늘어나면 이탈률 90%증가된다는 연구가 있다.
- 최소 3초 이내. 이상적으로는 1~2초 이내의 빠른 로딩 속도를 목표로

### 풀테이블 스캔이 발생하지 않도록 설계

비용이 매우 높기 때문

- 인덱스 활용
- 실행 계획 확인
- 작업 시간 분리

### 인덱스

- 책으로 비유하자면 맨 뒤에 찾아보기(색인) 페이지를 활용하여 찾는 시간을 줄임
    - 보통 가나다 순, 그리고 옆에 페이지 번호가 적혀있음
- 데이터베이스에선
    - 지정된 컬럼의 값과 해당 값을 가진 실제 데이터 행의 위치(주소값, 포인터, PK값 등)을 한쌍으로 지정
    - 인덱스 내부의 데이터는 **항상 정렬된 상태**
    - 데이터를 검색할땐 B-Tree/B+Tree(이진탐색트리) 자료구조를 사용

### 인덱스 생성, 조회, 삭제

```sql
CREATE INDEX 인덱스이름 ON 테이블 이름 (컬럼1, 컬럼2, ...);
```

결과

- Key_name: 인덱스의 이름
- Column_name: 인덱스거 어떤 컬럼을 기반으로 만들어졌는지 보여줌
- PRIMARY, (foreign key) 인덱스
    - 기본키, 외래키 제약조건을 설정하면 해당 컬럼에 대해 자동으로 인덱스를 생성함
- Non_unique: 1이면 중복 허용, 0이면 허용하지 않음
- Cardinality: 인덱스에 저장된 유니크한 값의 개수에 대한 추정치. 높을 수록 중복도가 낮아 인덱스의 성능이 올라감
- 유니크 제약 조건에 인덱스를 자동으로 생성되는 이유
    - 유니크 제약조건은 커럼 내 데이터의 유일성을 보장해야함.
    - 새 데이터를 삽입하거나 기존 데이터를 수정할 때마다 값이 테이블에 존재하는지 확인해야 함
    - 인덱스가 없다면 중복 검사를 위해 풀 테이블 스캔이 발생해 성능 하락

### 인덱스가 정말 사용되는지 확인하는 법(EXPLAIN)

```sql
EXPLAIN SELECT * FROM items WHERE item_name = '게이밍 노트북';
```

- type: ALL
    - type → 데이터베이스가 테이블에 어떻게 접근할지 나타냄
        - ALL → 풀 테이블 스캔. 처음부터 끝까지 다 읽음
        - ref → = 조건이나 JOIN에서 인덱스를 사용
        - RANGE → 범위 검색 (BETWEEN, >, <, 등)에서 인덱스를 사용
- key: key는 쿼리를 실행할 떄 사용한 인덱스. NULL은 인덱스를 사용하지 않음
- rows: 옵티마이저가 쿼리를 처리하기 위해 탐색할 것으로 예측하는 행의 수
- filtered: 테이블에서 읽어온 행들 중에서 WHERE 조건으로 필터링 되고 난 뒤 최종적으로 남을 것으로 예측되는 행의 비율
- Extra: 추가적인 정보

### 인덱스 사용처

- 동등 비교 (=)
- 범위 검색(BETWEEN, >, <, LIKE 등)
- ORDER BY를 통한 정렬

동등 비교

- type: ref → 동등 비교 조건이나 join에서 인덱스를 사용했을 때
- possible_keys: 쿼리에서 사용 가능한 인덱스 후보

FORCE INDEX → 인덱스를 강제로 적용

### LIKE 범위 탐색

검색어% 처럼 검색어가 먼저 나와야 검색 가능. (%검색어, %검색어%는 안됨)

- Full-Text Search: B-Tree인덱스와 달리 텍스트를 단어(토큰)단위로 쪼개서 인덱식싱. → 텍스트 중간에 있는 단어도 빠르게 검색 가능(%검색어%)

### 인덱스와 정렬

정렬(ORDER BY) 작업은 생각보다 비용이 많이 드는 작업

- filesort: 데이터를 찾고 그 결과를 다시 정렬하는 별도의 정렬 작업 → 이것을 피해야 효율적으로 가능
- 인덱스를 거꾸로 읽는 역방향 스캔(Backward Index Scan)을 해 내림차순으로도 정렬 가능
    - 보통 정방향 스캔이 역방향 스캔보다 아주 약간 빠름
        - 하드웨어의 미리 읽기(Prefetching)기능 때문에 정방향으로 읽을 것으로 예측하고 다음 데이터를 미리 준비해 두기 때문
- 내림차순 인덱스 생성 가능
    - 단일 컬럼 인덱스에는 성능 차이가 별로 안날 수 있지만, 여러 컬럼에 대해 서로 다른 정렬 순서(오름차순, 내림차순 혼함)이 필요한 복잡한 쿼리에서는 성능차이가 남

### 옵티마이저와 인덱스 선택

데이터베이스의 옵티마이저는 쿼리를 실행하기 전에 다양한 방법을 평가하고 가장 비용이 적게들 것이라 판단되는 방법을 선택. 인덱스를 사용하는게 오히려 비효율적이라 판단되면 풀 테이블 스캔을 선택할 수 있음.

### 인덱스 손익분기점

옵티마이저가 인덱스 사용 여부를 결정하는 기준.

- 인덱스를 사용하는 비용: 인덱스 탐색 비용 + 인덱스에서 찾은 주소로 테이블에 접근하는 비용(랜덤I/O)
- 풀 테이블 스캔 비용: 테이블 전체를 순차적으로 읽는 비용(순차I/O)

→ 일반적으로 전체 데이터의 약 20~25% 이상을 조회해야 하는 쿼리는 인덱스보다는 전체 테이블을 스캔하는게 더 효율적이라고 알려져 있음.

### 랜덤 I/O가 느린 이유

- 순차 I/O
    - 데이터가 저장된 위치를 찾으면 그 이후는 순서대로 읽으면 됨
    - HDD의 경우 헤드가 거의 움직이지 않고 연속된 데이터를 읽으므로 빠르고 효율적
    - SSD ‘여기에서 100개 읽어와’라는 하나의 큰 명령으로 처리할 수 있음
- 랜덤 I/O
    - 책의 페이지를 왔다갔다 하는 느낌
    - HDD의 경우 읽어야 할 데이터가 디스크 여러 곳에 흩어져 있어, 데이터를 읽을 때마다 디스크 헤드가 이동해야함. 데이터의 위치를 찾는데 걸리는 시간이 있어 느림
    - SSD의 경우 하나씩 읽어오는 작은 명령을 각각 여러번 처리해야함. 더 많은 부하.

### 인덱스가 여러개 있다면?

선택할 수 있는 인덱스 후보가 여러개라면 가장 효율적으로 작동하는 인덱스를 선택. 물론 풀 테이블 스캔이 인덱스들보다 더 효율적이라고 판단되면 풀 테이블 스캔을 선택함.

### 데이터가 많이 부족하다면?

풀 스캔 테이블을 선택할 가능성이 있다. 순차적으로 읽는 비용이 더 저렴하기 때문.

### 커버링 인덱스

기존 인덱스 방식에서 데이터 위치를 찾고 원본 테이블에 접근하는 과정은 랜덤 I/O기 때문에 비용이 발생함. 이 과정을 생략한 것.

→ **쿼리에 필요한 모든 컬럼을 포함하고 있는 인덱스**

- 일반 인덱스 → Extra: Using index condition
    - where 절을 필터링 하는덴 인덱스를 사용했지만, 최종 데이터를 가져오기 위해서는 추가 작업이 필요하다는 뜻
    - Using index condition: → WHERE 일부를 인덱스 스캔 중에 필터링
- 커버링 인덱스 사용 → Extra: Using where: Using index
    - 인덱스 스캔 단계에서 효율적으로 필터링이 되었다
    - Using index → 인덱스만 보고 끝냈다
    - Using where → 가져온 뒤 WHERE로 추가 필터링

### 커버링 인덱스 적용

컬럼이 여러개인 복합 인덱스에서 컬럼의 순서는 매우 중요. WHERE절에서 동등 비교나 범위 검색에 사용되는 컬럼을 가장 앞에 두어야 인덱스를 효율적으로 사용할 수 있음

- 장점
    - 압도적인 SELECT 성능 향상: 랜덤 I/O가 없기 때문
    - 특히 COUNT 쿼리 최적화: 테이블 전체가 아니라 크기가 작은 인덱스만 스캔해 빠름
- 단점
    - 저장 공간 증가: 원본 데이터와 별고듸 저장 공간 차지
    - 쓰기 정능 저하: INSERT, UPDATE, DELETE 작업 시 테이블 데이터뿐만 아니라 인덱스도 같이 수정해야 함.
- 언제 쓰면 좋나?
    - 조회(일기)가 매우 빈번하고, 쓰기 작업은 상대적으로 적은 테이블에 적용
    - SELECT 절에서 조회하는 컬럼의 개수가 적을 때 유리.
    - 성능 저하가 발생하는 특정 쿼리를 튜닝하기 위한 비장의 무기 느낌으로 사용

### 복합 인덱스(Composite Index)/다중 컬럼 인덱스(Multi-column Index)

조건이 여러개인 쿼리의 성능을 취적화하기 위해 사용.

- 컬럼 순서가 중요한 이유
    - 칼럼 순서대로 우선적으로 정렬
    - (category, price) 순서로 만들었다고 치면 category 먼저 1차로 정렬하고, 같으면 그 중에서 2차로 price 별로 정렬
    - **인덱스 왼쪽 접두어 규칙(Index Left-Prefix Rule)**
        - 인덱스를 (A, B, C) 순서로 생성했다면 WHERE 조건에 아래와 같이 사용될 때 효율적
            - (A)
            - (A, B)
            - (A, B, C)
        - (B), (C), (B, C)는 효율적으로 불가
    - **복합 인덱스 대원칙**
        - 인덱스는 순서대로
        - 등호(=) 조건은 앞으로, 범위 조건(>, <)은 뒤로
        - 정렬도 인덱스 순서를 따를 것
