### 1. 도커 이미지와 컨테이너

도커 엔진에서 사용하는 기본 단위는 이미지와 컨테이너

1. 도커 이미지
    
    컨테이너를 생성할 때 필요한 요소
    
    여러개의 계층으로 된 바이너리 파일로 존재, 컨테이너를 생성하고 실행할 땐 읽기 전용으로 사용
    
    도커 명령어로 이미지 내려받을 수 있음
    
    이름은 [저장소 이름]/[이미지 이름]:[태그]로 구성
    
    우분투 CentOS 등 기본적인 리눅스 운영체제부터 아파치 웹 서버, mysql 데이터베이스 등의 각종 애플리케이션, 하둡 스파크 등의 데이터 분석 도구까지 종류가 많음
    
2. 도커 컨테이너
    
    이미지로 컨테이너를 생성하면 이미지의 목적에 맞는 파일이 들어 있는 파일 시스템과 격리된 시스템 자원 및 네트워크를 사용할 수 있는 격리된 공간이 생성
    
    컨테이너끼리 영향을 주지 않음
    

### 2. 도커 컨테이너 다루기

1. 컨테이너 생성
    
    먼저 도커 엔진의 버전 확인
    
    컨테이너 생성 -i -t옵션 → 컨테이너와 상호 입출력 가능
    
    exit, ctrl+d → 컨테이너를 정지시키고 빠져나오기
    
    ctrl + p,q → 단순히 컨테이너에서 빠져나오기
    
    run 명령어 - docker pull(이미지 없으면) → docker create → docker start → docker attach(-i, -t)
    
    create 명령어 -  docker pull(이미지 없으면) → docker create
    
2. 컨테이너 목록 확인
    
    docker ps -  정지되지 않은 컨테이너만 출력. -a 옵션: 모든 컨테이너 출력
    
3. 컨테이너 삭제
    
    docker rm
    
    prune 명령어 -  모두 삭제
    
4. 컨테이너를 외부에 노출
    
    컨테이너는 가상머신과 마찬가지로 가상 IP주소를 할당 받음
    
    ifconfig - 컨테이너 네트워크 인터페이스 확인
    
    eth0 - 컨테이너가 외부와 통신할 때 쓰는 메인 이더넷 인터페이스
    
    lo - 컨테이너 자기 자신으로만 통신하는 내부 전용 인터페이스
    
    run의 -p 옵션으로  컨테이너의 포트를 호스트 포트와 바인딩해 연결
    
5. 컨테이너 애플리케이션 구축
    
    대부분의 서비스는 단일 프로그램으로 동작하지 않음
    
    컨테이너에 애플리케이션을 하나만 동작시키면 독립성 보장, 앱 버전관리, 소스코드 모듈화가 쉬워짐
    
    한 컨테이너에 프로세스 하나만 실행하는 것이 도커의 철학
    
    docker run -d옵션 (detached모드 - 터미널에 붙어있지 않고 백그라운드에서 실행)
    
    -i 옵션 : 표준입력을 열어둠: 컨테이너가 표준 입력을 받을 수 있음
    
    -t 옵션: 가상 터미널을 하나 만들어서 컨테이너에 할당 → 포어그라운드로 동작해서 보통 백그라운드에서 컨테이너가 동작하게 함
    
    -e 옵션: 컨테이너 내부의 환경변수 설정
    
6. 도커 볼륨
    
    도커 이미지로 컨테이너를 생성하면 이미지는 읽기 전용이 되며 컨테이너의 변경 사항만 별도로 저장해서 각 컨테이너의 정보를 보존
    
    이미 생성된 이미지는 변경되지 않음
    
    실수로 컨테이너를 삭제하면 데이터를 복구 할 수 없음 > 볼륨을 활용해 데이터를 영속적 데이터로 활용 가능
    
    1. 호스트 볼륨 공유-v 옵션 [호스트 공유 디렉터리]:[컨테이너 공유 데릭터리] → 호스트와 컨테이너 디렉터리 공유
        
        호스트의 볼륨을 공유하면 컨테이너 디렉터리가 덮어씌여짐
        
    2. 볼륨 컨테이너 - 볼륨을 사용하는 컨테이너를 다른 컨테이너와 공유
        
        —volumes-from
        
    3. 도커 볼륨
        
        도커 자체에서 제공
        
        [볼륨 이름]:[컨테이너의 공유 디렉터리]
        
        stateless - 컨테이너가 아닌 외부에 데이터를 저장하고 컨테이너는 그 데이터로 동작하도록 설계하는 것
        
7. 도커 네트워크
    1.  구조
        
        도커는 컨테이너에 내부 IP를 순차적으로 할당. 컨테이너 재시작할 때마다 변경 가능
        
        내부 IP는 도커가 설치된 호스트(내부 방) 에서만 쓸 수 있어서 외부와 연결할 필요가 있음 → weth~~ 라는 네트워크 인터페이스를 생성해 이루어짐
        
        eth0 - 공인 IP 또는 내부 IP가 할당되어 실제로 외부와 통신할 수 있는 호스트 네트워크인터페이스
        
        docker0 - 각 veth 인터페이스와 바인딩돼 호스트의 eth0과 이어주는 역할
        
    2. 기능
        
        컨테이너를 생성하면 기본적으로 docker0 브리지를 통해 외부와 통신할 수 있는 환경 사용 가능. 선택에 따라 여러 네트워크 드라이버를 쓸 수 있음
        
        도커가 제공하는 드라이버: bridge, host, none, container, overlay
        
        bridge - 컨테이너를 생성할 때 자동으로 연결되는 docker0 브리지를 활용하게 설정
        
        **브리지 네트워크** - docker0 브리지와 비슷하게 사용자 정의 브리지를 생성해 각 컨테이너에 연결하는 구조. 외부와 통신 가능
        
        disconnect, connect 자유롭게 끊고 연결 가능
        
        **호스트 네트워크** - 네트워크를 호스트로 설정하면 호스트의 네트워크 환경을 그대로 쓸 수 있음
        
        **논 네트워크** - 아무런 네트워크를 쓰지 않음
        
        **컨테이너 네트워크** —net 옵션으로 container를 입력하면 다른 컨테이너의 네트워크 네임스페이스 환경을 공유할 수 있음.
        
        내부 IP, 네트워크 인터페이스의 맥주소 공유
        
        **브리지 네트워크와 —net-alias** : 브리지 타입의 네트워크와 —net-alias옵션을 함께 쓰면 특정 호스트 이름을 컨테이너 여러개에 접근할 수 있음
        
        ping을 날리면 라운드 로빈 방식으로 컨테이너들 IP중 하나에 접근
        
        컨테이너 IP가 자주 바뀌니 이름으로 찾게 해주는 방식
        
        dig 도구 - DNS로 도메인 이름에 대응하는 IP를 조회할 때 사용
        
        MacVLAN 네트워크 - 호스트의 인터페이스 카드를 가상화해 물리 네트워크 환경을 컨테이너에게 동일하게 제공.
        
        컨테이너는 물리 네트워크 상에서 가상의 맥 주소를 가지고 해당 네트워크에 연결된 다른 장치와 통신 가능
        
    
    8. 컨테이너 로깅
    
    1. json-file 로그
        
        컨테이너 내부에서 어떤 일이 일어나는 지 아는 것은 디버깅 뿐만 아니라 운영 측면에서도 중요.
        
        앱 레벨이서 로그가 기록되게 할 수 있지만 도커 컨테이너의 표준출력, 에러 로그를 별도의 파일로 저장하고 확인할 수 잇음
        
        —tail n:마지막 n개, —since 유닉스 시간 이후부터
        
        —log-opt : json 로그 파일 크기 제한(로크파일이 커져서 용량 잡아먹는거 방지)
        
        로깅 드라이버들: syslog, journald, fluentd, awslogs
        
    2. syslog 로그
        
        유닉스 계열 운영체제에서 로그를 수집하는 오래된 표준 중 하나
        
        커널, 보안 등 시스템과 관련된 로그, 애플리케이션의 로그 등 다양한 종류의 로그 수집해 저장
        
    3. fluentd 로깅
        
        각종 로그 수집하고 저장할 수 있는 기능을 제공하는 오픈소스 도구
        
        수집되는 데이터를 AWS S3, HDFS, MongoDB등 다양한 저장소에 저장 가능
        
    4. 아마존 클라우드워치 로그
        
        AWS에서 로그 및 이벤트를 수집하고 저쟁하 시각적으로 보여주는 클라우드 워치 제공. 도커를 AWS EC2에서 사용하고 있다면 사용 가능
        
        사용 단계
        
        1. 클라우드 워치에 해당하는 IAM 권한 생성
        2. 로그 그룹 생성
        3. 로그 그룹에 로그 스트림 생성
        4. 클라우드워치의 IAM 권한을 사용할 수 있는 EC2 인스턴스 생성과 로그 전송

9. 컨테이너 자원 할당

run, create 명령어에서 자원 할당량을 조정하도록 옵션을 입력

옵션 없으면 제한 없지만 제품 단계의 컨테이너를 고려한다면 자원 할당을 제한해 다른 컨테이너 동작을 방해하지 않게 함

docker inspect

1. 컨테이너 메로리 제한
    
    docker run 명령에 —memory를 지정해 제한 단위는 m, g. 최소 6mb
    
    컨테이너 내부에서 동작하는 프로세스가 할당된 메모리를 초과하면 컨테이너는 자동으로 종료
    
    swap 메모리 - 메모리가 모자랄때 디스크에서 잠깐 빌려쓰는 공간
    
2. 컨테이너 cpu 제한
    
    —cpu-shares 옵선: 컨테이너에 가중치를 설정해 해당 컨테이너가 cpu를 상대적으로 얼마나 사용할 수 있는지
    
    기본값 1024 → cpu할당에서 1의 비중
    
    —cpuset-cpus: 호스트에 cpu가 여러개 있을 때 특정 cpu만 사용하도록 설정
    
    —cpu-period, —cpu-quota : CFS 주기(기본 100ms) 변경
    
    [—cpu-quota]값 / [cpu-period] 값 만큼 cpu 시간 할당
    
    —cpus 좀더 직관적으로 cpu개수를 지정
    

### 3. 도커 이미지

모든 컨테이너는 이미지를 기반으로 생성 → 도커 관리에서 이미지 다루는 건 중요

도커는 도커 허브(Docker Hub)라는 중앙 이미지 저장소에서 이미지를 내려 받음

1. 도커 이미지 생성
    
    docker commit [OPTIONS] CONTAINER [REPOSITORY[:TAG]]
    
2. 이미지 구조 이해
    
    이미지를 커밋할 때 변경된 사항만 새 레이어에 저장하고 그 레이어를 포함해 이미지를 생성하기 때문에 이전 파일 포함
    
    docker rmi로 이미지 삭제 가능하지만 이미지를 사용중인 컨테이너가 있으면 삭제 불가
    
    -f로 강제할 수 있지만 이미지 레이어 파일을 삭제하지 않고 이름만 삭제해 의미가 없음. 이미지의 이름이 None이 되고 → 댕글링 이미지라고 함
    
3. 이미지 추출
    
    도커 이미지를 별도로 저장하거나 옮기는 등 필요에 따라 단일 바이너리 파일로 저장가능
    
    docker save -o [파일명]
    
    추출된 이미지는 load로 로드 가능
    
    commit 명령어로 컨테이너를 이미지로 만들면 컨테이너에서 변경된 사항뿐만 아니라 생성될 때 설정된 detached 모드, 컨테이너 커맨드와 같은 컨테이너의 설정 등도 이미지에 저장됨.
    
    export명령어는 컨테이너 및 이미지에 대한 설정 정보를 저장하지 않음
    
4. 이미지 배포
    
    이미지를 다른 도커 엔진에 배포할 방법이 필요
    
    이미지를 단일 파일로 추출해서 배포할 수 있지만 이미지가 너무 크거나 도커 엔진이 많으면 이미지를 파일로 배포하기 어려움
    
    1. 도커 허브 이미지 저장소 사용
        
        push하고 pull만 하면 되므로 간단함
        
    2. 도커 사설 레지스트리
        
        사용자가 이미지 저장소를 만들 수 있음
        
        이미지 저장소 및 사용 서버, 저장공간 관리해야하는 번거로움
        

### 4. Dockerfile

1. 이미지 생성하는 법
    
    개발한 애플리케이션을 컨테이너화할 때 가장 먼저 생각나는 방법
    
    1. 아무것도 존재하지 않는 이미지(우분투, CentOS)로 컨테이너 생성
    2. 애플리케이션을 위한 환경을 서치하고 소스코드 등을 복사해 잘 동작하는 것을 확인
    3. 컨테이너를 이미지로 커밋
    
    → 일일이 수작없으로 패키지를 설치하고 소스코드를 복제하거나 호스트에서 복사해야함.
    
    이미지의 동작을 보장할 수 있음
    
    → 위 과정을 손쉽게 기록하고 수행할 수 있는 build 명령어 제공
    
    완성된 이미지를 생성하기 위해 필요한 것들을 하나의 파일에 기록해두면 이 파일을 읽어 컨테이너에서 작업을 수행한 뒤 이미지로 만들어 냄 → 이러한 작업을 기록한 파일의 이름을 Dockerfile이라고 함 빌드 및 배포를 자동화
    
2. Dockerfile 작성
    
    명령어는 보통 대문자
    
    FROM: 생성할 이미지의 베이스가 될 이미지. 반드시 한번은 입력
    
    LABEL: 이미지에 메타데이터 추가. key:value 형태
    
    RUN: 이미지를 만들기 위해 컨테이너 내부에서 명령어 실행
    
    ADD: 파일을 이미지에 추가
    
    WORKDIR: 명령어를 실행할 디렉터리
    
    EXPOSE: Dockerfile의 빌드로 생성된 이미지에서 노출할 포트 설정
    
    CMD: 컨테이너가 시작될 때마다 실행할 명령어 설정. Dockerfile에서 한 번만 사용할 수 있음
    
3. Dockerfile 빌드
    
    빌드 중 생성되는 임시 컨테이너는 buildkit이라는 별도의 프로세스에서 제어.
    
    CACHED: 이전에 빌드했던 dockerfile에 같은 내용이 있다면 새로 빌드하지 않고 그 명령어 이전까지 사용한 이미지 레이어를 활용해 이미지를 생성함
    
    캐시가 불필요한 경우: 깃 같은데서 clone할때 버전이 바뀌어도 고정된 소스를 사용함. → —no-cache 옵션
    
    - 멀티 스테이지를 이용한 빌드
        
        일반적으로 애플리케이션을 빌드할 때 많은 의존성 패키지와 라이브러리가 필요함 → 그냥 빌드하면 이미지의 크기가 매우 커짐
        
        멀티 스테이지: 하나의 Dockerfile 안에 여러 개의 FROM 이미지를 정의해서 빌드 완료시 생성될 이미지의 크기를 줄이는 역할
        
        alpine, busybox 이미지: 우분투에 비해 크기가 매우 작지만 기본적인 프로그램 실행에 필요한 필수적인 런타임 요소가 포함되어 있는 리눅스 배포판 이미지. → 경량화된 애플리케이션 이미지를 생성할 수 있음
        
    - 기타 명령어들
        
        ENV: Dockerfile에서 사용될 환경변수 지정.
        
        VOLUME: 빌드된 이미지로 컨테이너를 생성했을 떄 호스트와 공유할 컨테이너 내부의 디렉터리 설정
        
        ARG: build 명령어를 실행할 때 추가로 입력을 받아 Dockerfile 내에서 사용될 변수의 값을 설정
        
        USER: 컨테이너 내에서 사용될 사용자 계정의 이름이나 UID를 설정하면 그 아래 명령어는 해당 사용자의 권한으로 실행
        
        ONBUILD: 빌드된 이미지를 기반으로 하는 다른 이미지가 Dockerfile로 생성될 때 실행할 명령어 추가
        
        STOPSIGNAL: 컨테이너가 정지될 때 사용될 시스템 콜의 종류 지정
        
        HEALTHCHECK: 이미지로부터 생성된 컨테이너에서 동작하는 애플리케이션의 상태를 체크하도록 설정. 
        
        컨테이너 내부에서 동작 중인 애플리케이션의 프로세스가 종료되지는 않았으나 애플리케이션이 동작하고 있지 않은 상태를 방지하기 위해 사용가능
        
        ADD, COPY: 로컬 디렉터리에서 읽어들인 컨특스트로부터 이미지에 파일을 복사하는 역할. 
        
        COPY: 로컬의 파일만, ADD: url, tar파일도 가능
        
        ENTRYPOINT, CMD: 컨테이너가 시작될 때 실행할 명령어 설정.
        
        차이점: entrypoint는 커맨드를 인자로 받아 사용할 수 있는 스크립트의 역할
        
        entrypoint에 항상 실행할거 고정하고, cmd에는 자주 바뀔 수 있는 것을 씀
        
        JSON 형태와 일반 형식 차이: 
        
        일반 형식은 셸(/bin/sh -c)를 거쳐서 실행, json은 프로그램을 직접 실행(exec from)
        

5. Dockerfile로 빌드할 때 주의점

좋은 습관들

하나의 명령어를 \로 나눠서 가독성 높이기

빌드 캐시를 사용해 기존 새용했던 이미지 레이어를 재사용하는 방법

RUN 하나당 하나의 이미지 레이어가 됨 → 크기 커짐. &&로 하나의 명령어로 묶으면 줄일 수 있음

다른사람이 빌드한 이미지에 불필요한 이미지 레이어가 들어있다면 export, import를 활용해 컨테이너를 이미지로 만들어서 크기를 줄일 수 있음. → 이전 이미지에 저장되어 있던 설정은 잃어버림

### 5. 도커 데몬

1. 도커의 구조
    
    컨테이너나 이미지를 다루는 명령어: /usr/bin/docker에서 실행
    
    도커 엔진의 프로세스 : /usr/bin/dockerd 파일로 실행되고 있음 
    
    클라이언트로서의 도커, 서버로서의 도커
    
    도커엔진: 외부에서 API 입력을 받아 도커 엔진의 기능을 수행. 도커 프로세스가 실행되어 서버로서 입력을 받을 준비가 된 상태를 도커 데몬이라고 함
    
    도커 클라이언트: 도커 데몬은 API입력을 받아 도커 엔진의 기능을 수행. 이 API를 사용할 수 있도록 CLI를 제공하는 것이 도커 클라이언트
    
2. 도커 데몬 실행
    
    service docker start
    
    service docker stop
    
    dockered - 도커 데몬 실행
    
3. 도커 데몬 설정
    
    dockered 명령오로 집적 실행하는 것보다 도커 설정 파일을 수정한뒤 도커 데몬이 설정 파일을 읽어 서비스로 실행되게 하는 것이 일반적
    
    1. 도커 데몬 제어: -H
        
        도커 데몬의 API를 사용할 수 있는 방법 추가
        
        기본: /var/run/docker.sock 사용
        
        IP주소와 포트 번호를 입력하면 원격 API Docker Remote API로 도커를 제어할 수 있음.
        
        TLS 인증으로 악용 방지
        
        여러개의 도커 데몬을 번갈아 가면서 사용해야 하는 경우: docker context 기능 활용 
        
    2. 도커 데몬에 보안 적용: —tlsverify
        
        바인딩된 IP주소와 포트 번호만 알면 도커를 제어할 수 있음
        
        ca.pem,  server-cert.pem, server-key.pem, cert.pem, key.pem 총 5개 파일
        
    3. 도커 스토리지 드라이버 변경: —storage-driver
        
        특정 스토리지 백엔드 기술을 사용해 도커 컨테이너와 이미지를 저장하고 관리→스토리지 드라이버
        
        도커 컨테이너가 이미지를 불변(immutable)인 읽기 전용 파일 시스템으로 사용할 수 있게 만들어줌
        
        스토리지 별로 컨테이너와 이미지 관리(스토리지 드라이버가 바뀌면 기존 이미지는 사용할 수 없음)
        
        스토리지 드라이버의 원리
        
        컨테이너 내부에서 읽기와 새로운 파일 쓰기, 기존 파일 쓰기 작업이 일어날 때는 Copy-on_write개념이 사용
        
        스냅숏-원본은 읽기 전용으로 사용하고 이 파일이 변경되면 새로운 공간을 할당
        
        스토리지를 스냅숏으로 만들면 어느파일이 스냅숏의 어느 위치에 저장되어 있는지 저장.
        
        그리고 이 스냅숏 안의 파일에 변화가 생기면 변경된 내역을 따로 관리해 스냅숏 사용.
        
        도커 이미지: 스냅숏의 원리를 통해 컨테이너 레이어 관리
        
        OverlayFS 드라이버 
        
        대부분의 운영체제에서 도커 설치하면 자동으로 설정되는 드라이버
        
        lowerdir: 도커의 이미지 레이어
        
        upperdor: 컨테이너 레이어. 컨테이너에서 발생한 변경 사항을 담고 있음
        
        크기가 큰 파일에 처음으로 쓰기 작업을 수항핼 때는 upperdir에 복사하는 시간으로 인해 작업 수행 지연이 생길 수 있음 → 컨테이너 내부에서 읽기 쓰기가 많이 발생하면 도커 볼륨을 사용해보기
        
        여러 계층의 이미지 레이어가 존재하는 것이 아니며 이미지 레이어를 하나의 컨테이너 마운트 지점에서 통합해 사용
        
        btrfs 드라이버
        
        리눅스 파일 시스템 중 하나. SSD 최적화, 데이터 압축 등 다양한 기능 제공
        
        파일 시스템을 별도로 구성하지 않으면 도커에서 사용할 수 없고 /var/lib/docker 디렉터리가 btrfs 파일 시스템을 사용하는 공간에 마운트 되어 있어야 함
        
        이미지와 컨테이너를 서브볼륨과 스냅숏 단위로 관리
        
        가장 아래에 있는 베이스 레이어가 서브 볼륨이 되고, 위에 쌓이는 자식 레이어가 베이스 레이어에 대한 스냅숏으로 생성
        
        ZFS 드라이버
        
        brtfs처럼 압축, 레플리카, 데이터 중복 제거 등 다양한 기능 제공
        
        안정성 초점. 무거워서 호스트에서 자원 사용량 확인
        
    4. 도커 데몬 모니터링
        
        여러 가지 이유로 모니터링을 해야 함.
        
        많은 수의 도커 서버를 효율적으로 관리
        
        도커로 컨테이너 애플리케이션을 개발하다가 문제가 생겼을 때 원인 찾기
        
        도커를 PaaS로서 제공하기 위해 실시간으로 도커의 상태 체크
        
        도커 엔진 자치가 지원하는 기능도 있고, 도커 프로젝트에서 지원하는 상용 솔류션 및 각종 오픈소스 대시보드도 있음
        
        1. 도커 데몬 디버그 모드
            
            도커 데몬에서 어떤 일이 일어나고 있는지 가장 확실하고 정확하게 알아내는 방법
            
            → 원하지 않는 정보까지 너무 많이 출력됨, 호스트에 있는 파일을 읽거나 도커 데몬을 포그라운드 상태로 실행해야 한다는 단점
            
        2. events, stats, system df
            
            events: 도커 데몬에 일어나고 있는 일을 실시간 스트림 로그로 제공
            
            컨테이너, 이미지 관련, 볼륨, 네트워크, 플러그인 등에 관한 명령어 수행 결과 출력
            
            stats: 실행 중인 모든 컨테이너의 자원 사용량을 출력
            
            system df: 도커에서 사용하고 있는 이미지, 컨테이너, 로컬 볼륨의 총 개수 및 사용중인 개수, 크기, 삭제함으로써 확보 가능한 공간 출력.
            
        3. CAdvisor
            
            컨테이너로서 간단히 설치할 수 있고 컨테이너별 실시간 자원 사용량 및 도커 모니터링 정보를 시각화해서 보여줌.
            
            오픈소스
            
    5. 파이썬 Remote API 라이브러리를 이용한 도커 사용
        
        -H 옵션을 원격의 도커 데몬을 제어하기 위해 사용하는 것도 좋지만 컨태이너 애플리케이션이 수행해야할 작업이 많거나 애플리케이션 초기화 등에 복잡한 과정이 포함돼 있으면 도커를 제어하는 라이브러리를 사용해 쉽게 해결 가능
